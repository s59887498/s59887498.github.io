QA 與需求交付流程說明

為了讓需求從規劃、開發到測試都能有一致的標準，並降低遺漏、誤解與上線風險，我們會依照以下流程推進。
這樣安排的目的，不只是把事情做完，而是確保每個階段都有清楚的輸入、產出與責任分工，讓團隊可以更有效率地協作。

→ Backlog Refinement（PM）

→ Test Plan Creation（QA）

→ Story Point Estimation（QA）

→ Sprint Planning（PM）

→ Planning Review / QA Alignment（QA）

→ Test Case Design（QA）

→ Test Case Review（QA）

→ Testing（QA）

→ Bug tracking（QA、RD、PM）

→ Test Report Design（QA）

流程階段

Owner

說明

為什麼要這樣做

主要產出

Backlog Refinement

PM

在需求正式進入開發前，先整理需求內容、商業目標、使用情境、流程、限制條件與驗收標準，確保需求具備可理解性與可執行性。

若需求定義不清，後續的開發、測試與估點都容易失準，也會增加來回確認與重工成本。透過前期 refinement，可以讓團隊先建立共同認知，降低規格模糊帶來的風險。

Refined backlog、需求說明、驗收標準

Test Plan Creation

QA

QA 根據已釐清的需求內容，先建立測試計畫，定義測試範圍、測試重點、風險項目、測試方式，以及所需的測試環境與資料。

測試不應該等到開發完成後才開始思考。提早規劃測試策略，可以提前識別高風險模組與相依項目，也有助於團隊事先準備必要資源，避免測試階段手忙腳亂。

Test Plan、測試範圍、風險清單

Story Point Estimation

QA

QA 依需求複雜度與測試範圍，評估測試設計、執行、驗證 bug、回歸測試與報告整理所需的工作量。

若只估 RD 開發工作量，容易忽略 QA 實際投入成本，造成 sprint 排程失衡。將 QA 工作量納入估點，有助於資源安排更合理，也能讓整體交付時程更貼近實際。

QA Story Point、測試工時評估

Sprint Planning

PM

PM 根據需求優先級、團隊資源與估點結果，安排本次 sprint 要完成的需求與交付目標。

Sprint Planning 的目的不只是排工作，而是讓團隊清楚知道本次迭代的優先順序與交付範圍。透過明確規劃，可降低 scope 過大、承諾過多或時程不合理的風險。

Sprint Backlog、Sprint Goal

Planning Review / QA Alignment

QA

在 sprint 開始前，QA 再次確認需求理解、測試時程、相依條件、環境準備與測試重點，並與 PM / RD 做必要對齊。

即使需求已進入 sprint，若 QA 對時程、測試條件或需求細節認知不一致，仍可能影響後續執行。此步驟可確保開發節奏與測試節奏一致，避免交付前才發現準備不足。

QA Alignment 結論、測試排程、風險提醒

Test Case Design

QA

QA 根據需求與測試計畫，設計具體測試案例，涵蓋正常流程、異常流程、邊界條件、權限驗證、資料驗證與跨模組影響。

測試案例是將測試想法具體化的核心資產。透過完整設計，可降低測試遺漏與判斷不一致的情況，也能作為後續回歸測試與自動化測試的重要基礎。

Test Cases、測試資料、覆蓋範圍

Test Case Review

QA

測試案例完成後，由 QA 進行 review，必要時可與 PM / RD 一同確認案例是否完整、合理且符合需求邏輯。

在正式測試前先 review，可提早發現測試缺漏、情境不合理或規格理解偏差，避免到執行階段才大幅調整，提升整體測試品質與效率。

Review 結果、修正版 Test Cases

Testing

QA

QA 依據測試計畫與測試案例執行測試，驗證功能是否符合需求、流程是否正確，以及既有功能是否受到影響。

Testing 不只是找 bug，而是驗證系統是否真正符合商業需求與使用情境。透過有系統的執行，可提早發現功能異常、整合風險與回歸問題，作為版本品質判斷依據。

測試結果、缺陷紀錄、執行狀態

Bug Tracking

QA / RD / PM

測試中發現的問題需被正式記錄、分類、指派、修復、回測與追蹤，並由相關角色共同管理狀態與優先級。

若缺陷只靠口頭溝通，容易造成遺漏、重複修正或責任不清。透過正式追蹤機制，可讓問題透明化、狀態可視化，也能作為後續版本風險管理與品質分析的依據。

Bug List、缺陷狀態、修復紀錄

Test Report Design

QA

測試完成後，QA 彙整測試範圍、執行結果、缺陷狀況、風險項目、未完成項目與最終建議，形成測試報告。

Test Report 不只是測試紀錄，而是提供 PM、RD 與 stakeholder 做版本判斷的重要依據。透過清楚的報告設計，可讓品質狀況被有效溝通，支援是否上線或是否需補強的決策。

Test Report、風險摘要、Release 建議
