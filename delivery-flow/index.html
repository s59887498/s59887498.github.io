01 / 先從 QA 的入口與出口

我收到什麼，
做到哪裡可以交？

先把工作與完成點講清楚，日期才有共同的比較依據。

01

入口：這張卡要完成什麼？

PM 已建 Story／SubStory 並安排預估開始／結束日。功能開發在 Daily 交棒，RD 說明版本、環境、自測與限制，QA 確認 RT 接手。

誰交？做什麼？原訂何時完成？
02

完成：先對齊完成條件

RD 從 My Tasks 勾自己的 SubStory 完成；QA 在 PreProd（Stage Testing）確認本次功能有包含、回歸 Passed，完成必要複驗及報告。各工作卡完成不等於 Story 已 Done。

做到什麼程度，才留實際完成日？
03

出口：下一位接得到

Bug 維持 QA 主單下的子任務；PreProd 由 RD 核對完整後通知 QA；QA 確認功能涵蓋與回歸 Passed，再交 PM／UAT 窗口，接 Ready To Release 的 Prod 準備。

交給誰？附什麼？對方收到嗎？

最少操作：PM 建卡與預估排期；RD 在 My Tasks 做完勾完成，留下實際完成日。Daily 再確認功能交棒與 Story 泳道，能否完成當下給明確答案；開發或上版問題即時回報 PM，不等 Daily。

06 / 已確認的建卡與交棒方式

PM 建卡排期，
RD 勾完成，Daily 接下一棒。

Story / PM 建立

PM 管需求與整體排程

PM 建立 Story，確認範圍、驗收與日期。Story 依 11 個泳道追蹤整體交付，子卡勾完不自動代表 Story Done。

SubStory / PM 建立

PM 拆工作並預估日期

這裡的 SubStory 指 PM 拆出的工作子卡，指定負責人、工作內容與完成條件。RD 在 My Tasks 看自己的卡、做完勾完成；功能交棒等 Daily 確認。

QA 主單 → Bug 子任務

Bug 用子任務已確認

保留 QA 主單下的多張 Bug，分別交 RD 修復與 QA 複驗。Bug 是工作子任務，不是另外新增的 Story 泳道；未過沿原單退回。

Asana／試跑準備

沿用 My Tasks 與 Daily，日期保留原訂。

  1. PM 建立及排期：Story／SubStory 由 PM 開立，寫工作、完成條件、負責人與預估開始／結束日，初次確認後保留原訂。
  2. RD 完成自己的工作：在 My Tasks 勾 SubStory 完成。勾選日期與真正實際完成日的留存方式需確認；不把勾子卡視為 Story 自動換泳道。
  3. Daily 功能交棒：RD 說明版本、環境、自測及限制，確認 QA 接手與下一步，由約定窗口更新 Story。誰移卡、Daily 前後的缺件處理方式列入試跑確認。
  4. 泳道與日期實測：驗證 11 個泳道、主子卡關聯、完成／重開日期、原訂與改期歷程。自動帶完成日、通知與報表彙整仍屬待驗證功能。

08 / 會議 Q&A

有人提問，
點開一起確認。

日期與完成點是這次共識；分派、放行與自動化的實務做法由試跑確認。

01目前已確認的分工是什麼？＋

Story、SubStory 都由 PM 開立及安排預估開始／結束日。RD 從 My Tasks 看自己的工作、做完自行勾完成；功能交棒在 Daily 確認。Bug 已確認用子任務。

02Story、SubStory 與 Bug 是什麼關係？＋

Story 是需求主卡；SubStory 在這裡指 PM 拆出的工作子卡，指定負責人與日期。QA 測試主單底下可掛多張 Bug 子任務，維持既有關聯。SubStory 是此流程的工作稱呼，不代表已設定新的 Asana 原生類型。

03誰開 SubStory、誰預估日期？＋

由 PM 開立並安排預估日期；各職能提供範圍、依賴及風險讓 PM 評估。執行中日期受影響，回 PM 協調，保留原訂、新日期與原因。

04RD 平常只看 My Tasks，可以嗎？＋

可以，沿用目前做法：PM 指派 SubStory，RD 從 My Tasks 看自己的工作與日期，符合完成條件後自行勾完成，不要求 RD 重複維護所有主卡資訊。

05RD 勾 SubStory 完成，Story 就往下移嗎？＋

不直接移。勾選代表 RD 自己的工作完成；Story 可以仍在 Development。功能交棒等 Daily 確認後，再由約定窗口更新到 Ready to RT Test。

06Daily 功能交棒要確認什麼？＋

版本、環境、自測結果、已知限制、驗收內容、QA 接手人與下一步。缺件或日期影響在同卡說明；實際交棒日期另留，不改寫 RD 已完成工作的日期。

07誰更新 Story 的泳道？＋

泳道順序已確認；實際由 PM、交付人或指定窗口移卡，這部分留給團隊在試跑前對齊。網站不把 RD 勾 SubStory 自動等同移 Story。

08最新泳道順序是什麼？＋

Product Backlog → Refinement → Sprint Backlog → Development → Ready to RT Test → RT Testing → Ready to Stage Test → Stage Testing → Pending UAT → Ready To Release → Done。

09Ready to RT Test 和 RT Testing 有什麼差別？＋

Ready to RT Test 是 Daily 已確認功能交棒、等待 RT 開測；RT Testing 是 QA 已開始測試。Ready to Stage Test 與 Stage Testing 也同樣區分待開測與已開測。

10RT 和 Stage 的測試範圍已經定好了嗎？＋

這次先確認泳道順序，RT 保留團隊用語。Stage Testing 的環境已確認為 PreProd。維運先準備、RD 核對有無漏上並通知 QA，QA 同時確認功能涵蓋及回歸 Passed；RT 的細部範圍與其他門檻仍依團隊約定。

11Pending UAT 由誰驗收？＋

PM 協調指定的 UAT 驗收窗口與條件；實際人選及核准權責尚待團隊確認。QA 交報告不代表 UAT 已通過；結果確認後才進 Ready To Release。

12Ready To Release 就是 Done 嗎？＋

還不是。Ready To Release 是驗收與發版條件確認後，等待或安排發布。維運上 Prod 後，沿用既有上線驗證與回報程序，PM 確認整體結案條件才進 Done。

13設計和測試準備放哪裡？＋

依需要由 PM 拆成 SubStory，可在 Refinement 或 Sprint 規劃時提早進行。它們是工作子卡，不另外新增 In Design 或 Test Planning 的 Story 泳道。

14所有 SubStory 都勾完，就能自動把 Story 標 Done 嗎？＋

不能只靠勾選判斷。Story 還要看必要測試、UAT 結果、發版及既有結案條件；由 PM 確認整體 Done。

15Bug 放 QA 主單下當子任務已確定嗎？＋

已確認使用子任務。沿用 QA 主單下多張 Bug 的方式，QA 主單 Owner 保留 QA；每張 Bug 分別留版本、日期與修復／複驗紀錄。

16RD 修好 Bug，就直接勾 Bug 完成嗎？＋

Bug 的完成條件要與開發 SubStory 分開。本 Demo 以 QA 已驗證為完成點；RD 修好先附版本與自測交複驗，通過再記 Bug 完成日。實際勾選與關閉權責在試跑時確認。

17Bug 來回也一定要等 Daily 嗎？＋

Daily 用於功能交棒與明確決議，不要求每張 Bug 等開會才處理。開發／上版問題要即時回報 PM；Bug 修復、複驗及急件回覆沿既有流程。

18Bug 複驗未過怎麼辦？＋

沿同一張 Bug 子任務留本輪版本、結果與 evidence，退回 RD；保留前輪紀錄。Story 是否需要退回 Development、或留在測試階段，依團隊約定，不新增 Bug 泳道。

19提前、準時與 Delay 怎麼判斷？＋

以同一張卡的實際完成日對照原訂結束日。原訂 10/16，10/14 完成提前 2 天，10/16 準時，10/19 Delay 3 天。日期差採日曆天，包含週末。

20到期還沒完成，實際日期怎麼填？＋

實際完成日維持空白。原訂當天顯示今日到期；隔天仍未完成才顯示逾期待完成。不得把預估日期當成實際完成日。

21RD 做完和 Daily 不同天，要用哪一天？＋

RD SubStory 留真正工作完成那一天；Daily 功能交棒另留交棒日期。例如 10/14 做完、10/15 Daily 交棒，RD 完成日仍為 10/14，Story 在交棒確認後再進待 RT 測試。

22改期之後，原訂日期會消失嗎？＋

不會。原訂開始／結束保留，PM 與相關窗口確認新時程、原因及日期。原訂 10/16、新交期 10/20、實際 10/19：對原訂 Delay 3 天，對新交期提前 1 天。

23日期區間可以當成實際工作量嗎？＋

不直接換算。這次記排程與交期達成，不增加每日工時填報；日程區間可能包含依賴、會議、驗收或等待安排。

24各 SubStory 或 Bug 的 Delay 能相加嗎？＋

不能相加成 Story 的整體延期。各卡比自己的原訂日期，Story 比自己的整體交期；並行工作可能重疊。Delay 原因與責任另外看紀錄。

25Asana 已經自動帶完成日、移卡與通知了嗎？＋

目前網站為模擬，沒有正式串接。RD 現有 My Tasks 勾選方式沿用；完成／重開日期、原訂保留、通知及深層報表需要實測，不宣稱勾子卡已自動移 Story 泳道。

26OP 也一定要有設計 SubStory 嗎？＋

不需要就不建空白設計工作。Story／SubStory 的 PM 分工照已確認規則，OP 收單沿既有入口；是否需某測試／驗收階段由團隊門檻判斷，不自動略過。

27兩週試跑要先對齊哪些事情？＋

選專案、5–10 張卡、PM 及各組窗口、開始日；確認各工作完成點、Daily 交棒內容、Story 移卡窗口、RT／Stage 進出門檻、UAT 驗收安排與改期規則。兩週後回顧可追溯性、交棒及操作負擔。

28後續怎麼接 KPI 或插單治理？＋

先確認資料及完成點一致，再談交期達成率或其他指標。插單由共同窗口與 PM 協調，記被影響工作、新日期及原因；Priority 與 Bug 嚴重程度分開，個人考核用途另議。

29PreProd 上好後，QA 可以直接開始回歸嗎？＋

先由 RD 核對本次應上功能／修復與版本是否齊全、確認沒有漏上，完成後主動通知 QA，再由 QA 執行功能涵蓋確認與回歸。維運完成準備不直接等於 QA 已接手。

30QA 在 PreProd 要回覆哪兩個結果？＋

一是本次應上功能是否確實包含，二是回歸測試是否 Passed。兩項都要明確記錄，附版本、範圍與結果；只說「測完」不足以交付後續 Prod 準備。

31PreProd 漏上或回歸未過，能繼續準備 Prod 嗎？＋

先停在未完成的交接點，即時回報 PM，保留問題與 Bug 關聯，讓 RD／維運處理。更新 PreProd 後由 RD 重新核對並通知 QA，再確認功能涵蓋與回歸結果；未通過不直接往 Prod。

32Daily 上主單還有 Bug，要怎麼做決議？＋

先明確回答現在能不能完成／交付。不能就說明未結 Bug 與阻斷原因、處理人、預計可完成或下次回覆時間，並提出需要 PM 協調的事項。

33時程影響還不清楚，要等 Daily 才通知 PM 嗎？＋

不用等。上版或開發一發現問題就先回報 PM，說明已知影響與目前處理人；時程與原因確認後再補，讓 PM 能及早規劃。

09 / 可照著講

五分鐘會議講稿

更新：2026/10/30。以下約五分鐘，語氣比較口語、委婉。操作提示不用念出來。

0:00–0:40 先說明這次想確認什麼 ＋

操作：停在首頁「最新結論」。

今天想跟大家確認的，主要是工作怎麼交接，以及有問題時，怎麼讓下一位和 PM 及早知道。

希望透過這個流程，讓大家比較清楚：我現在要完成什麼、做到哪裡可以交出去，以及下一步由誰接手，盡量減少反覆詢問。

目前已確認的分工會繼續沿用：Story 和 SubStory 由 PM 建立、安排預估日期；RD 平常從 My Tasks 看自己的工作，完成後勾選，功能交棒再於 Daily 確認。

這次主要把後面的 PreProd 上版順序，以及問題回報方式補得更清楚。

0:40–1:40 PreProd 的交接順序 ＋

操作：切到「完整工作流 → PreProd → Prod」。

先從 QA 的角度來看，我們需要知道：什麼時候可以開始測？收到的是哪個版本？這次應該包含哪些功能？

目前確認的順序是，RT 測試完成後，先由維運準備 PreProd。

維運準備好之後，先請 RD 對照這次應上的功能和 Bug 修復，確認內容齊全、沒有漏上，再通知 QA，並附上版本和範圍。

QA 接到這個交棒後，會確認兩件事：

第一，這次應上的功能確實有包含；第二，回歸測試結果是 Passed。

交付時把這兩個結果說清楚，後面的人就比較容易判斷，是否已經符合接著準備 Prod 的條件。

1:40–2:20 對照泳道，看下一棒在哪裡 ＋

操作：指向 PreProd 區段上方的泳道對照。

這裡也確認一下，PreProd 就是 Stage Testing 使用的環境。

所以，Ready to Stage Test 是維運準備、RD 核對並通知 QA；QA 實際進行功能確認和回歸，就是 Stage Testing。

確認通過後，再接 Pending UAT 的既有驗收、放行確認，接著進 Ready To Release，由維運準備上 Prod。

上 Prod 後，沿用既有的上線驗證和結果回報，再由 PM 確認結案條件，才進 Done。

各組可以透過泳道，知道目前走到哪裡、下一步等誰接手。

2:20–3:15 站立會議留下明確的下一步 ＋

操作：回首頁「站立會議」與「即時回報 PM」。

站立會議的部分，希望每張主單都能更清楚地確認：目前能不能完成、能不能交給下一位？

如果可以，就確認交付內容和接手人；如果還不行，也請說明卡在哪張 Bug、為什麼影響交付、由誰處理，以及預計何時完成或再回覆。

我們希望會議結束時，每個人都知道下一步，而不是還需要另外找人確認。

另外，開發或上版遇到問題，也請即時回報 PM，不用等下一次 Daily。

即使還不確定會影響幾天，也可以先說明目前發生什麼事、誰在處理、何時補充結果，讓 PM 能提早安排時程和協調資源。

3:15–4:05 Bug 往返與日期怎麼留下來 ＋

操作：看問題處理說明，再切交期 Demo。

如果 PreProd 發現漏上、功能不齊，或回歸沒有通過，就先回報 PM，交由 RD、維運處理。更新後，再由 RD 核對並通知 QA，確認新的版本和測試結果。

Bug 繼續放在 QA 主單下，作為各自的子任務。複驗沒過，就沿同一張 Bug 留下結果，再交回修復，保留每一輪的版本和交接紀錄。

日期的部分，我們看的是交期。例如原訂十六號完成，十四號完成是提前，十六號是準時，之後完成就是 Delay。

如果需要改期，原訂日期會保留，再補新日期和原因。這樣 PM 和各組才能一起看懂，原本怎麼安排、後來為什麼調整。

4:05–5:00 最後希望大家同意的試跑方式 ＋

操作：回到「先試兩週」。

接下來想請大家一起確認，是否可以先選一個專案、五到十張卡，試跑兩週。

試跑前，希望先對齊幾件事：版本和應上範圍放在哪裡、各組怎麼通知下一位、由誰確認接手，以及 Story 由誰更新泳道。

PreProd 的部分，就依今天確認的順序交接；站立會議留下能否完成的答案、負責人和回覆時間；遇到開發或上版問題，及時讓 PM 知道。

兩週後，我們再一起看看：交接有沒有更清楚、問題有沒有更早被看見、日期是否容易追溯，以及操作上會不會增加大家負擔。

希望先用小範圍，把最常卡住的地方做順，再依大家實際使用的情況調整。
