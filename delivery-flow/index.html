用來解釋日程的三種區段

有在推進？在等？被中斷？

實際設定方法 / 導入前由窗口設定一次

Asana 先建兩種工作類型。

大家使用已設定好的選項；不要求每個人自己建立欄位或規則。

  1. 進專案 → 自訂（Customize）選任務範本（Task templates）→ 新增 → 新類型（New type）。
  2. 建立「職能工作」待開始／處理中／等待／暫停／完成，只有「完成」標為已完成。
  3. 建立「Bug」待修復／修復中／待 QA 複驗／已驗證，只有「已驗證」標為已完成；複驗失敗回待修復。
  4. 套用到實際卡片，試走一次既有卡與深層 Bug 也要確認類型、欄位及統計專案範圍。RD 修好交 QA 複驗；QA 主單 Owner 不變。

跨職能：完成 RD 開發卡 → 指定 QA 測試卡接手人，QA 尚未開測就待開始。

同一張 Bug：RD 修復中 → 待 QA 複驗、改派 QA → QA 驗證通過才完成。

自訂類型／狀態支援 Starter 以上，設定需專案管理員或編輯權限；官方操作說明 ↗。若需要原生 Estimated time／Actual time，需 Advanced 以上並啟用工時功能；官方工時與父子加總說明 ↗。我們尚未確認你們帳號的方案、權限與深層報表範圍。

設定狀態不等於自動啟動投入人時計時，也不等於已完成所有工作日曆或 KPI 統計。正式試跑前，用一張 QA 主單與兩張 Bug 驗證：層級、明細歸屬、加總和報表是否都正確。

交接規則：主卡、子卡、Bug 怎麼維持秩序？ ＋

主卡保留需求、驗收標準與交期；必要交付完成、阻斷問題已處置、Prod 驗證完成後才結案。

職能子卡一張可交接工作對應一位 Owner。退回沿用原卡，並行工作各自保留狀態。

Bug 修復卡掛在本次 QA 主單下，可有多張。Bug 修好轉待複驗並指派 QA；QA 主單仍由 QA 負責，投入依原始紀錄分 QA／RD。

等待與插單只暫停受影響工作；等待的對象與實際處理者分開，不把等待自動視為任何人的人時。

07 / 會議 Q&A

先把問題說清楚，
找到最少必要的記錄。

點選問題展開說明。以下是試營運建議，正式規則待大家共同確認。

先確認目的

投入多少工時，可以靠完工補登；交付為什麼延後，需要交接與狀態歷程。先確認要回答哪些問題，再決定記哪些資料。

Asana 狀態怎麼設？多張 Bug 怎麼算？和 Notion 如何對應？
01只是記時間，做完再補填花了幾小時，不就好了？＋

可以。如果目的只是統計投入工時，完工補填是很直接的方式。

但填了八小時，仍不知道這件事為什麼過了一週才交付。中間可能在等規格、等修復，或被插單。

所以我們需要先確認：維運要的是「投入多少工時」，還是也需要知道「交付時間花在哪裡」，再選擇最少必要的記錄方式。

02完工補填一定不準嗎？＋

不一定。短、單純、很快完成的任務，補填可以很實用。跨很多天、反覆切換的工作，回想時可能漏掉會議或修復時間，因此可在自己的子任務交付時補登，不必等整個功能上線才回想。

如果數字是憑印象回估，也應保留「回估」註記，讓報表使用者知道資料性質。

03那只記狀態，就能得到準確的實際工時嗎？＋

不能。任務標示「處理中」五小時，不代表某個人連續投入五小時。

狀態紀錄提供流程經過時間；工時補登提供人員回報的投入時間。如果維運必須比較預估人時與實際人時，就需要另加投入紀錄。Demo 的多 Bug 情境另外補登 QA 4、RD 5 人時，與處理中區段分開。

04預估和實際，到底要比較哪兩個數字？＋

要用相同單位比較：

  • 預估投入八人時，要跟回報投入的人時比較。
  • 預計週三交付，要跟實際交付日期比較。
  • 預估階段跨度兩個工作天，要跟同一套日曆下的實際跨度比較。

不能把「實際經過三天」直接拿來跟「預估八人時」比較。

05所以我們要同時填工時、改狀態，工作不就更多了？＋

這是試營運要驗證的重點，不能先保證操作一定更少。

建議沿用原本就需要更新的進度狀態，避免主卡、子卡重複填寫；如果確定需要投入工時，再於子任務交付時確認一次。兩週後檢查這些資料有沒有用，以及維護負擔是否值得。

06PM、UIUX、RD 一起開一小時會議，要怎麼算？＋

如果三個人都完整參與，投入合計是三人時；但這件事在交付時間軸上，只經過一小時。

能明確歸屬某個需求的會議，就記在相關工作；無法合理歸屬的跨專案會議，可以另列共用工作，避免硬拆出看似精準的數字。同一筆投入也不能在子卡和主卡重複加總。

07等別人回覆時，我在做另一件事，時間算在哪裡？＋

原任務留下「等待」區段；實際投入則記到正在處理的另一件工作。

因此，一張卡等待八小時，表示它被阻擋了八小時，並不代表負責人整天沒做事，也不代表被等待的對象投入了八小時。

08QA 發現 Bug，退回 RD，工時和責任怎麼分？＋

QA 測試、複驗的投入記在 QA 主單自身；多張 Bug 開在本次 QA 主單下，RD 修復投入各記在 Bug 卡。QA 等修復的區段另外呈現，不把多張 Bug 的重疊等待相加。

QA 主單仍由 QA 負責；Bug 修復時指派 RD，修好後轉待 QA 複驗並指派 QA。投入歸屬看原始明細，不因 Bug 目前改派給 QA 就把 RD 工時改算給 QA。

09我一天被插很多次單，每次都要操作嗎？＋

建議先記錄會影響交接或排程的正式工作切換，例如原本的開發被暫停，改去處理另一張 OP Issue；不要求每則訊息、每次短暫詢問都記。

緊急處理時可以先處理，再補上關聯與時間，並註明補記。哪些切換值得記，會在試跑時一起調整。

10忘記改狀態，算出來不也一樣不準？＋

對，狀態紀錄也需要維護，不能因為自動計算就當成準確。

發現漏記時要能更正，保留補記或估計註記。試營運也要抽查：紀錄是否符合實際交接，而不只是看欄位有沒有填滿。

11主卡、子卡到底誰負責維護？＋

建議主卡由需求或收單 Owner 管理需求、驗收條件與承諾日期；各職能只維護自己的子卡。

主卡進度預計由工具彙整。工具還沒支援的部分，先指定一個窗口處理，並把這份額外負擔納入試營運評估，避免每個人都重複更新。

12QA 測完就能結束嗎？OP Issue 也要走完整流程嗎？＋

職能完成和整體交付分開：QA 可以完成自己的子卡，主卡則等必要交付及 Prod 驗證完成後結案。

OP Issue 依實際需要建立子卡。沒有設計變更，就可以略過 UIUX；小修復不必硬套完整功能開發流程。

13插單先後誰決定？嚴重的 Bug 一定優先嗎？＋

第二階段需要共同議定收單與核准窗口，讓優先順序有一致入口。

嚴重程度說明問題影響，Priority 決定處理順序，兩者需要一起判斷。核准插單時，也要說清楚被延後的是哪件工作，並重新確認交期。

14這些紀錄會拿來考核嗎？做越久，表現越差嗎？＋

建議這兩週先用來檢查資料品質與協作流程，並在會議上明確記錄用途。

耗時會受到工作複雜度、需求變更、等待與插單影響，不能單憑時間長短評分個人。後續如何銜接 KPI，需要另外確認定義、資料與使用規則。

15網站已經能自動串 Asana、產生報表了嗎？＋

目前網站是互動示範，交接、狀態與補登人時都是模擬資料，尚未串接正式 Asana。

試跑前要先確認現有帳號的功能、權限和設定，再驗證哪些可以直接完成、哪些需要額外處理。工具成本與維護負擔，都應納入評估。

16兩週後怎麼判斷要不要繼續？如果補填工時就夠呢？＋

選五到十張任務，檢查三件事：各組需要的數字是否拿得到、關鍵等待與插單能否追溯、大家花多少時間維護。

如果完工補填已經足以回答維運的需求，就保留簡單方式；如果還需要改善交接和排程，再保留有用的狀態紀錄。

17Asana 的「待開始、處理中、完成」要怎麼設定？＋

建議由專案窗口設定一次：進入專案的自訂 → 任務範本 → 新增 → 新類型，建立「職能工作」與「Bug」兩種類型，再定義各自的狀態，以及哪些狀態代表完成。既有卡片也要套用對應類型。

職能工作平常走「待開始 → 處理中 → 完成」，受阻才用等待或暫停。Bug 走「待修復 → 修復中 → 待 QA 複驗 → 已驗證」；RD 修好仍待驗，不直接標完成。

查看頁面內設定步驟。依 Asana 官方文件，自訂任務類型需 Starter 以上及相應編輯權限；本頁未讀取或變更公司的 Asana 設定，試跑前先確認方案與權限。

18QA 主單下掛很多張 Bug，維運還能拉出時間嗎？＋

可以按這個結構設計報表：功能／OP 主卡 → QA 測試、複驗與報告主單 → 多張 Bug 子任務。QA 主單記測試與報告，各 Bug 記 RD 修復；維運透過關聯取得整個交付包。

Demo 已回報的例子是 QA 4 人時、RD 修兩張 Bug 共 5 人時，交付包合計 9 人時。9 是這個包的合計，不能全當 QA 工時，也不能再加一次 Bug 明細。未記錄的前期規劃及其他職能不包含在這 9 人時。

Asana 原生工時可顯示子任務彙總，但公司帳號的多層子任務、報表篩選與權限仍要用「一張 QA＋兩張 Bug」實測。若直接用父卡目前負責人分類，容易把包內 RD 投入誤歸 QA。

19Bug 修好指派給 QA，先前 RD 的工時會不會變成 QA 的？＋

報表應依每筆投入的記錄者、當時職能與工作內容分類，不依卡片目前指派給誰倒算。指派代表現在輪到誰接手，不代表整張卡的所有歷史都是他的投入。

例如 RD-A 在 BUG-01 回報修復 3 人時，之後指派 QA 複驗，這 3 人時仍屬 RD。此 Demo 的 QA 複驗投入記在 QA 主單自身；同一份投入只記一次，避免主單與 Bug 重複。

20這些時間和 Notion 的 QA Wait、Cycle Time 是同一件事嗎？＋

要逐項對口徑。原頁的 QA Wait Ratio 寫的是 Waiting for QA，也就是等 QA 開始測試；不能把 QA 已開測後等 RD 修 Bug 的八小時直接塞進去。Deploy Wait 則依 Ready for Deploy 到 Production 的起訖衡量。

Notion 的 Ticket 建立、各職能開始與完成時點仍待確認。本 Demo 採「需求建立至 Prod 驗證」呈現整體交付，尚未宣稱等同正式 Cycle Time 分母；有並行工作時也不能把各組時間直接相加算占比。

查看逐項對照及待確認定義。先收集交接歷程，再和指標窗口一起確認可以計算哪些數字。

21能不能就「開始切狀態，做完指派給下一位」這麼簡單？＋

可以，這就是推薦大家先學會的操作。拿到卡先確認；真的開始才切處理中；交付時換狀態、確認下一位接得住。只有卡住或被插單，才多選原因。

交棒有兩種：跨職能時，RD 完成開發卡，確認 QA 的工作卡及接手人；同一張 Bug 則由 RD 修好後轉待 QA 複驗、指派 QA。QA 主單仍由 QA 管理測試與報告，不需要整張主單來回改給 RD。

狀態變更提供流程時間。如果維運還需要實際投入人時，再於交付時補登自己的投入，這是另一份資料。

22為什麼要分處理、等待和中斷？Notion 有要求三個都記嗎？＋

分開是為了解釋日程差異：工作在推進、卡在等條件、還是被核准插單暫停，改善方式不同。只留下開始與結束，無法分辨是哪種原因造成延後。

不是 Notion 原頁已要求這三類都當 KPI。原頁有開發、Review、QA、等 QA 與待部署等指標；「插單中斷」及「QA 等修復」是這次建議補記的診斷資料。

試跑先記會影響交接或排程的等待與中斷；兩週後再刪掉沒有用途、負擔太高的記錄，不要求每次短暫分心都切狀態。
