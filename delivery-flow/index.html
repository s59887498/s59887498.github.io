預估開始／結束

先約定工作時程

實際完成

改期紀錄

新安排與原承諾並列

05 / Bug 往返，完成點與交期一起說清楚

同一張 Bug 追到底，
修好後還要複驗。

QA 主單下可以掛多張 Bug，各張分別排期與交接；QA 主單由 QA 負責。

01

RD 交修復，是交接點

留修復版本、自測與交付日期，交指定 QA。Bug 仍為待複驗，實際完成日先空白。

02

QA 通過，Bug 才完成

本提案以已驗證為 Bug 完成點。未過就在原 Bug 留本輪結果退回 RD，保留每輪版本與日期。

03

再修影響交期，要協調

保留原訂交期，再記新時程、改期原因與確認窗口；同步看是否影響 QA 報告及上線日期。

04

分派與回覆，一起約定

由 QA 指派 RD，或 RD 窗口分派？複驗怎麼排？哪些問題影響交付？由 QA／RD 與相關窗口確認。

06 / 把分工落在主卡、子卡

每張卡都說清楚，
做什麼、何時交、交給誰。

功能／OP 主卡

需求 Owner 管整體交付

範圍、整體驗收、原訂時程與改期歷史。必要交付及 Prod 驗證完成後，留下主卡實際完成日。

職能子卡

各組管自己的完成點

工作內容、完成條件、Owner、預估開始／結束、實際完成、下一位與交付內容。RD 交付 QA、QA 交付維運，各有自己的日期。

QA 主單 → 多張 Bug

各 Bug 分別約定交期

修復、複驗與各輪結果留 Bug；QA 主單追蹤必要測試、複驗與報告交付。各組日期不相加，也不要求人人重填主卡。原訂初次確認時保留，後續改期才加紀錄。

Asana 試跑準備

先備好卡片內容，再驗證日期留存。

  1. 建立共用模板：工作內容、完成條件、Owner、交付對象與必要資料。依工作需要建立職能卡與 Bug。
  2. 確認日期欄位：預估開始／結束日、保留的原訂開始／結束日、實際完成日。改期另留新時程、原因及確認窗口，不覆蓋原訂。
  3. 少量進度即可：一般用待開始／進行中／完成；Bug 增加待複驗、需再修、已驗證。接手、完成、交棒與改期時才更新必要資訊。
  4. 正式上線前實測：完成與重新開啟時的日期留存、通知與收到回覆、深層子任務及報表範圍。自動帶完成日及彙總屬待驗證功能，目前 Demo 只示意。

08 / 會議 Q&A

有人提問，
點開一起確認。

日期與完成點是這次共識；分派、放行與自動化的實務做法由試跑確認。

01這次主要想記錄什麼？＋

工作內容、完成條件、Owner、預估開始／結束日、實際完成日及交接。核心是確認有沒有依原訂交期完成。

02預估日期區間，代表花了多少工作量嗎？＋

預估開始至結束是排程區間，包含依賴、會議或排隊等安排；日程跨度不能直接當成個人工作量。

03提前、準時與 Delay 怎麼判斷？＋

以同一張卡的原訂結束日比較實際完成日。原訂 10/16，10/14 完成是提前 2 天，10/16 是準時，10/19 是 Delay 3 天。

04到期當天還沒完成，算 Delay 嗎？＋

本 Demo 以 Asia/Taipei 的日期判斷：10/16 當天尚未完成顯示「今日到期」，10/17 仍未完成才顯示「逾期待完成」。實際完成日保持空白。若工作需要特定截止時刻，試跑時另行約定。

05有預估日期，就能直接填實際完成日嗎？＋

實際完成日依已完成的事實填寫，達成卡片完成條件才記。尚未完成保留空白；回補時用真正完成那一天，不能把預估日期當作實際日期。

06改交期之後，原訂日期會消失嗎？＋

不會。原訂開始／結束日保留；每次改期另記新時程、日期、原因和確認窗口。畫面同時看對原訂及對目前交期的結果。

07原訂 10/16，改到 10/20，10/19 完成算什麼？＋

對原訂是 Delay 3 天，對目前交期是提前 1 天。兩者並列，讓原承諾與新安排都能被看見。

08改期誰確認？可以自己把日期往後移嗎？＋

試跑先約定確認窗口，例如需求 Owner 與受影響的職能窗口。提出新日期時附原因、依賴及影響；確認後再更新目前排程，保留原訂基準。

09是不是每天都要操作卡片？＋

在接手、開始、完成、交棒及改期時更新必要資訊。一般進度用待開始／進行中／完成；臨時開會、接電話或換工作不用逐次切暫停。

10需要另外填工時嗎？＋

這次試跑以時程和交付日期為主，卡片先記必要日期、完成條件與交接，不增加每日工時填報。

11主卡和子卡的完成日一樣嗎？＋

不一定。各職能卡依自己的完成條件記日期；功能／OP 主卡在必要交付及 Prod 驗證完成、需求 Owner 確認後結案，不能拿最早完成的子卡日期替代。

12RD 開發卡做到哪裡算完成？＋

本提案是可測版本、環境、自測與必要交付內容已交 QA，並確認接手。若團隊想以其他門檻為準，需在卡片與試跑開始前對齊。

13QA 主單要等每一張 Bug 都關閉嗎？＋

依必要測試與放行條件判斷。阻斷問題需處置；非阻斷項目若有共同確認的處置，可在報告列明。誰可放行、哪些可後續追蹤，由相關窗口約定。

14QA 主單下可以放多張 Bug 嗎？＋

可以。每張 Bug 各有工作、完成條件、負責人、預估日期與交接歷程。QA 主單 Owner 保留 QA，不受影響的測試可以繼續。

15RD 修好，就把 Bug 標完成嗎？＋

本提案以 QA 已驗證為 Bug 完成點。RD 修好先附版本、自測並轉待複驗，留修復交付日期；QA 通過後才留 Bug 實際完成日。

16Bug 複驗未過，或關閉後又重新開啟怎麼辦？＋

未過沿用原 Bug 留本輪結果、版本與日期，退回 RD。若已關閉後重開，前次完成紀錄仍保留，現在進度改回未完成，最後通過日另外留存；原訂基準不變。完成／重開的日期留存方式需在 Asana 實測。

17每張 Bug 的 Delay 可以相加嗎？＋

不能相加成整體功能的延後天數。每張卡分別比自己的交期，主卡比自己的整體交期；多組或多 Bug 的日程可能重疊。

18Asana 需要準備哪些欄位？＋

先用共同模板寫清工作、完成條件與交接，再確認預估開始／結束、保留的原訂開始／結束、實際完成日及改期原因的記錄位置。完成日自動帶入、重新開啟、深層子任務與報表範圍都需先實測。

19現在會自動記日期、通知和彙總嗎？＋

目前網站只有模擬功能，沒有正式 Asana 串接。試跑前先驗證實際欄位、完成／重開事件、通知與收到回覆；自動化保留原訂與改期歷程屬待配置工作。

20Delay 就代表負責人表現不好嗎？＋

日期結果先用來看交付與調整；需求變更、上游依賴、Bug 或插單的原因需一起看。個人考核的用途與規則另行議定。

21RD 被插單，原本的工作怎麼處理？＋

由共同收單與核准窗口協調優先順序，連回被影響的卡，保留原訂日期並記原因、新交期及確認窗口。Priority 與 Bug 嚴重程度分開。

22會直接對接 Notion KPI 嗎？＋

先確認日期資料與完成點一致，再討論交期達成率等指標。只有預估／完成日期不能直接得出 Active、Wait 或完整工作量；需要其他指標時另定資料來源與計算口徑。

23兩週試跑要同意哪些事？＋

最想改善的問題、試跑專案及 5–10 張卡、各組窗口和開始日、每張卡完成點、原訂與改期規則、交接通知與收到回覆方式。兩週後一起看資料是否可追溯、交接與額外操作負擔。

24日期差有扣週末或國定假日嗎？＋

這版用完整日期比較，差異顯示日曆天，包含週末與假日。例如週五原訂、週一完成是 Delay 3 天。若公司要看工作天，需另訂一致的工作日曆；提前／準時／Delay 的日期比較不變。

09 / 可照著講

五分鐘會議講稿

操作提示不用念；各角色快速切換，不需要播放全部步驟。

0:00–0:35 開場與目的 ＋

操作：停在首頁。

今天想跟大家分享一個初步方向，希望讓工作交接更清楚，也讓主管容易確認事情有沒有照約定日期完成。

這次想先把每張卡的工作內容、完成條件和交期說清楚，再用實際完成日，確認是提前、準時，還是 Delay。這份 Demo 方便大家討論，實際做法也希望配合各組習慣一起調整。

0:35–1:20 QA 的入口與出口 ＋

操作：看「先從 QA 的入口與出口」。

以 QA 為例，入口就是：誰把單交給我、版本和環境在哪裡、這張卡要測什麼，以及預計哪一天完成。

RD 交付時，把版本、自測和驗收內容放在同一張卡，指定 QA 接手。QA 回覆可以接，或說明還缺什麼，並確認日期。

出口則是：有 Bug 就交 RD 修復；必要測試、複驗和報告完成後，再把版本、報告和限制交維運，請對方確認收到。

1:20–2:10 各組的工作與完成點 ＋

操作：切到「完整工作流」，快速切換「各角色走一遍」，再回主頁。不必逐步播放全部角色。

其他組也可以用同樣方式。PM 交需求和驗收標準，UIUX 交可實作的設計，RD 交可測版本與自測，QA 交測試結論，維運交部署和 Prod 驗證結果。

每組的完成點會不一樣。例如 RD 的開發卡交付 QA 後可以完成；QA 卡要做到必要測試和報告交付；功能主卡則等 Prod 驗證通過，再確認結案。

所以每張卡先確認三件事：要做什麼、怎樣算完成、完成後交給誰，再約定自己的開始和結束日期。

2:10–3:05 日期判斷與改期 ＋

操作：主頁「交期 Demo」選提前、準時，再選「改期保留原訂」，按「看完整結果」。

例如 QA 原訂十月十日到十六日做這件事，十四日完成就是提前，十六日完成是準時，十九日才完成就是 Delay。超過十六日還沒完成，就先顯示逾期待完成，實際完成日保持空白。

如果後來需要改期，就保留原訂十六日，再記下新的日期、改期原因和確認窗口。

像新交期改成二十日、十九日完成，對新安排是提前一天，但對原訂仍是 Delay 三天，兩個資訊一起看，主管才知道承諾怎麼變動、為什麼調整。

3:05–4:00 Bug 往返與最少操作 ＋

操作：選「多 Bug／複驗退回」，看完整結果並點 BUG-01。

Bug 比較容易來回，所以這裡示範在 QA 主單下開多張 Bug，各自有負責人、完成條件和交期。

RD 修好交 QA，是交接點；這份提案以 QA 複驗通過，作為 Bug 的完成點。未通過就沿原單退回，保留每輪版本與結果。如果影響交期，再一起確認新日期和原因，也看是否影響報告或上線。

大家平常的操作就是：接手確認內容和日期，開始時更新進行中，完成時留完成日並交棒。臨時開會照常進行，交期真的有影響再協調。

4:00–5:00 兩週試跑的共識 ＋

操作：停在「先試兩週」。

如果大家覺得方向有幫助，想邀請先選一個專案、五到十張卡，試跑兩週。
